# v0.4.1

Not released yet: these notes collect what's on `main` since 0.4.0. A new tool may make this
0.5.0; that's the release's call.

## Tool descriptions say when to use each tool

`list`, `stale` and `verify` now say when to use them rather than a sibling tool. Found by
Glama's review of the 0.4.0 tool definitions, which scored these three lowest. Each lost a
point for leaving the choice between tools to the agent.

- **`list`** browses the tree and returns page summaries, not text. It points to `read` for
  a page's text and to `search` for finding pages by what they say. It also says what
  happens when both `path` and `type` are given: `type` is used, as it always was.
- **`stale`** is for finding what to re-verify, or which team to ask about a page. It says
  that none of its pages can be cited, that deprecated pages aren't listed, and that the
  owners fix a page with `verify` or `propose_edit`.
- **`verify`** confirms a page as it stands and changes nothing else. It says to use
  `propose_edit` when anything in the page is wrong, and to verify once that change is
  merged.

Only the words change: no tool's arguments, results or refusals change. The benchmark
presents only `search` and `read`, whose descriptions are as before, so bench rounds stay
comparable.

## `check_pr`: follow up on a proposal

A new read-only tool. Give it the `pr_number` that `propose_edit`, `verify` or `draft_page`
returned, and it says whether that pull request is open, merged or closed. It also gives its
reviews (the latest approval or change request per reviewer) and the page it touches. An agent
can now check that an edit merged before it verifies the page, or before it proposes the same
change again. Found by Glama's review, which marked the tool set down for leaving the write
lifecycle open-ended.

- **What it shows is what the caller may see.** The PR's own files decide which pages it
  touches, never its branch name. Each must be a page the caller can see, on the default branch
  where it's there and as the PR's head has it. A PR touching a page you can't see, or one
  without a Docsworth PR's shape (its branch, base and files), is reported as not found, the
  same as a number with no PR. The shape isn't proof of who opened it, so check the number
  your own write returned.
- **It answers to `read`:** a policy that refuses `read` refuses `check_pr` too.
- **Token scopes:** it needs *pull requests: read* as well as *contents: read*. Classic `repo`
  covers both.
- **The audit log** records `pr_number`, and as returned only pages whose id came from the
  default branch.
- **The verify-page skill** now checks that an edit merged before it verifies.

## Retiring a page

`propose_edit`'s description says how: `edits` that replace the page's `status:` line with
`status: deprecated`. A deprecated page is never cited, `search` lists it under `excluded`, and
`stale` stops listing it. The server always allowed it; nothing said so.
