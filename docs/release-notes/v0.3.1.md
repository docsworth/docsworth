# v0.3.1

A fix for the CI workflow `docsworth init --ci` writes. Everything else is as in 0.3.0.

## The CI workflow

- **It was red for everyone without Docsworth pro,** on the first push and on every pull
  request, since 0.2.0. It ran `docsworth compile`, which is pro's, and CI runs the
  published CLI through `npx`, which never has pro. So `compile` exited 2: "compile is part
  of Docsworth pro, which isn't installed".
- **Now it lints and runs no pro command.** One job runs `docsworth lint .` on pull requests
  and on pushes to `main`, over the knowledge pages, CODEOWNERS and
  `.knowledge/config.yaml`, with read-only repository access. It no longer commits to your
  repo.
- **A repo that already has the workflow keeps the old one,** since `init` never
  overwrites. Delete `.github/workflows/knowledge.yml` and run `docsworth init --ci` again,
  or remove its two `compile` steps and the `compile` job yourself.
- **Compiling runbooks into skills in CI** needs pro installed there, which this workflow
  doesn't do.

## The docs

- The README's command table marks pro's commands. Without pro, each exits 2 and says so.
- The rollout guide says what the workflow runs, and marks the weekly digest as pro.

## How it was found

0.3.0 was installed as a new user would, with an empty home directory, nothing from a clone
and no `DOCSWORTH_*` variables:
- the CLI from npm;
- the Claude Code plugin through the marketplace, which answered a question citing a page;
- `init --ci`'s workflow in a new GitHub repository, where both runs failed.

The packed CLI's tests now run every step of the workflow `init --ci` writes, with the CLI
alone, as CI does. In that repository, the fixed workflow's push and pull-request runs
passed.
