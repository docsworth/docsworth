# v0.3.2

The MCP server is ready for the MCP registry. The web app and the CLI say plainly what
Docsworth pro adds, and the CLI says when it's installed but can't load. The mirror docs
say where Notion's boundary is.

## The MCP registry

- **`server.json` describes the MCP server** for the
  [MCP registry](https://registry.modelcontextprotocol.io): `io.github.docsworth/docsworth`,
  run as `npx -y @docsworth/cli@0.3.2 mcp` over stdio. There `DOCSWORTH_KNOWLEDGE_DIR` is
  required, since a registry client starts the server from any directory. `GITHUB_TOKEN` is
  optional; without it the server uses `GH_TOKEN`, then `gh auth token`.
- **`package.json` carries `mcpName`,** which the registry checks against the listing. The
  release guard refuses a release whose listing names another version or package, or isn't
  the package's `mcpName`, in the repository and in the packed tarball.
- The listing itself is published to the registry separately, after this release.

## Docsworth pro, as the web app and the CLI report it

- **`docsworth serve` tells the web app which pro commands are installed.** Settings says
  "installed: …" or "not installed", and the overview's note on what pro adds shows only
  without it. A pro that's installed but can't be used is named once on `serve`'s stderr,
  and the server runs without it.
- **A pro that can't find the CLI by its package name says so in one line,** with what to
  do, instead of a stack trace.

## The example

- **`examples/acme` turns the audit log on,** kept in your state directory, outside the
  checkout. With pro, `docsworth usage-report examples/acme` then has something to show
  once you've used the example.

## The docs

- **What the mirror skips:** the data inventory, the enterprise README and the format spec
  now say it's Confluence pages with read restrictions, and their descendants. On Notion
  there's no per-page check: sharing with the integration is the boundary (under
  `root_page_ids`, if set). The security model already said so.
